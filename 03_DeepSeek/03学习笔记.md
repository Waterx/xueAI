# 03 的精华：一个字从 LLM 到页面，经历了什么？

这节真正要弄清楚的是三个问题：**网络上传什么、SDK 在本地补充什么、后端向前端转发什么。** 分清这三层，chunk、delta、snapshot 和异步生成器就能串起来。

## 1. 追踪一个字：“按”

假设之前的回答是“……SSE ”，模型又生成了“按”：

```text
DeepSeek
    │ 网络传来一个响应片段：delta.content = "按"
    ▼
后端里的 SDK
    │ 将“按”拼到本地已有文本上
    │ 得到 snapshot = "……SSE 按"
    │ 提供 chunk、content.delta 等 SDK 事件
    ▼
model.py / stream_reply
    │ 提取文本：yield "按"
    ▼
main.py / POST /chat
    │ 重新包装：event: delta
    │           data: {"text": "按"}
    ▼
浏览器
      answer.textContent += "按"
      页面显示“……SSE 按”
```

**一个新增字经过了：模型响应格式 → Python 字符串 → 应用 SSE 格式 → 页面文字。**

这里有两段网络连接：DeepSeek ↔ 后端，以及后端 ↔ 浏览器。SDK 就在后端 Python 进程里运行，不是另一个远程服务。

## 2. /chat 就是你说的“中转包装站”

前端只需知道“收到 delta 就追加”，不用知道 DeepSeek 的 choices、SDK 的事件结构或 API Key。

```python
# model.py：从 SDK 事件中提取文字
if event.type == "content.delta":
    yield event.delta

# main.py：将文字包装成前端认识的 SSE
async for text in chunks:
    yield sse("delta", {"text": text})
```

这两处 delta 不是同一个协议：`content.delta` 是 SDK 的事件类型；`event: delta` 和 `{"text": ...}` 是我们给前端定义的格式。

**model.py 隔离模型差异，/chat 稳定前端协议。** 所以 02 用固定模板、03 用真实模型，前端仍然可以用同样的代码。将来换模型，也可以保持“逐段 yield str”这个约定。

## 3. 最重要的发现：日志里的全文是本地 SDK 拼出来的

你看到的日志：

```json
{
  "type": "content.delta",
  "delta": "按",
  "snapshot": "……SSE 按",
  "parsed": null
}
```

容易让人以为：LLM 每生成一个字，都把之前的全文重新传一遍。

实际情况是：**上游传增量，本地维护累计状态。**

| 本次网络收到的新增文本 | SDK 本地的 snapshot |
| --- | --- |
| SSE | SSE |
| 按 | SSE 按 |
| 事件 | SSE 按事件 |

可以把 SDK 的累积工作想成 `snapshot += new_text`。打印整个事件对象时，也把它在本地算出来的 snapshot 打印了。

因此：**日志里有某个字段，不代表这个字段的内容全部来自本次网络传输。**

浏览器又维护了一份全文：SDK 的 snapshot 服务于后端处理，DOM 的 textContent 服务于页面展示。

```javascript
// 增量：追加
answer.textContent += payload.text;
```

如果使用累计全文，则应覆盖输出框。把 snapshot 每次都追加会导致：

```text
正确：SSE → SSE 按 → SSE 按事件
错误：SSE → SSESSE 按 → SSESSE 按SSE 按事件
```

## 4. chunk 和 content.delta：同一个片段的两种入口

本项目使用 SDK 的高层流助手 `.chat.completions.stream(...)`。收到含有文本的片段后，SDK 通常会给代码提供：

```text
一个上游模型片段
    ├── chunk 事件：详细片段 + 完整响应快照
    └── content.delta 事件：新增文本 + 全文字符串
```

可以理解为“详细视角”和“文本专用视角”。它们是两个独立事件对象，模型只生成了一次内容。

| content.delta 事件 | chunk 事件中的对应信息 |
| --- | --- |
| event.delta | event.chunk.choices[0].delta.content |
| event.snapshot | event.snapshot.choices[0].message.content |

注意 chunk 事件内部的布局：

```text
SDK event
├── chunk       上游响应片段，例如新增“按”
└── snapshot    SDK 本地累积的完整响应对象
```

**原始片段和累计快照是并列字段。** `snapshot.message.content` 中出现全文，不代表 `chunk.delta.content` 也传了全文。

“content.delta 是 chunk 的一部分”从信息上大致成立；从对象结构上，更准确的是：SDK 从同一个上游片段提取出独立的文本事件。

我们的需求只是显示回答，所以只处理 content.delta。若同时从两类事件取出文字并追加，会把同一段文字处理两遍。

正常完成时还有 content.done，携带全文。parsed 是结构化输出解析相关字段，普通文本场景下为 null。

## 5. stream_reply：等一段，交一段，再等下一段

核心只有这几行：

```python
async for event in stream:
    if event.type == "content.delta":
        yield event.delta
```

**async for 负责等待输入，yield 负责交出输出。**

```text
main.py 请求下一段 text
    → stream_reply 开始或继续执行
    → 等 SDK 提供下一项
    → yield "按"，暂停并交回 main.py
    → main.py yield SSE 字符串，交给响应框架
    → 框架发送内容，再请求下一项
```

yield 会保留执行位置，下一次从暂停处继续；它不会直接把内容写入浏览器。最终由 StreamingResponse 迭代生成器、发送 HTTP 响应。

### 调用不等于开始执行

```python
chunks = stream_reply(prompt)
```

因为 stream_reply 是包含 yield 的 async def，这一步只得到异步生成器对象。main.py 开始 `async for text in chunks` 时，才执行读取 Key、连接模型等函数体代码。

### 异步解决的是“等待期间怎么办”

等待网络时，当前任务可以让出执行机会，服务器可以处理其他请求。同一个回答仍按顺序处理，不是每个字开一个线程。

| 语法 | 在这条链路里的含义 |
| --- | --- |
| async def + yield | 定义可以边等待、边产出的异步生成器 |
| async for | 逐个获取数据，没有下一项时可以异步等待 |
| yield | 交出一项，暂停并保留进度 |
| await | 等一次异步操作完成，再执行下一行 |
| async with | 管理资源，退出时进行异步清理 |

外层 async with 管理 HTTP 客户端，内层管理本次模型流。`await stream.get_final_completion()` 获取 SDK 汇总的最终响应，不会再次让模型回答。

## 6. 三种单位不能混为一谈

| 层次 | 单位 | 含义 |
| --- | --- | --- |
| 模型 | token | 生成和计量的单位，不等于汉字数 |
| 模型接口 | chunk | 一段响应，可包含文本或工具调用信息 |
| 底层网络 | 数据包 | 传输单位，边界不等于 chunk 或 SSE 事件边界 |

一个 chunk 不必对应一个 token。一次网络读取也可能只有半条 SSE 事件，或同时含多条事件，所以前端必须缓冲并按空行解析。

event 是带类型的事件；message 是对话中的一条消息。LLM 与 Agent 的交互没有一个所有层次通用的“基本单位”。

### chunk 并没有负责排序的递增 ID

- id：整次回答的标识，同一次生成的多个片段通常共用它。
- choices[0].index：回答候选的索引，不是片段序号。
- created：时间戳，也不是片段序号。

本项目依赖底层 TCP 保证字节按序可靠交付，再由 HTTP/SSE 和 SDK 解析。当前使用的 Chat Completions chunk 没有逐块递增的序号。

### 丢包和漏处理不是同一件事

| 情况 | 后果 |
| --- | --- |
| 偶发底层丢包 | TCP 重传，可能短暂停顿 |
| 网络持续故障 | SDK 报错或超时，回答停在已收到的位置 |
| 应用漏发、漏处理某段 | 可能缺字，TCP 无法纠正应用逻辑 |

**snapshot 只能累积收到的内容，不能恢复没收到的内容。** 当前没有断点续传，max_retries=0 也关闭了 SDK 自动重试。重新提问是一次新的生成。

## 7. max_tokens=64 实验：硬上限不等于篇幅规划

我们让模型写长回答，它却在“触发 message 或自定义”处停止，没有自动收束成完整短句。

| 控制 | 职责 |
| --- | --- |
| 提示词：“请用一句话回答” | 引导模型规划简短内容 |
| max_tokens=64 | 输出达到上限就停止，哪怕句子没结束 |

模型可以提前结束，不会凑满额度；想得到完整短回答，需要提示词引导，并留足 token 预算。

达到限制时通常会有 `finish_reason="length"`。实测中，高层 SDK 抛出了 LengthFinishReasonError，main.py 再转换成通用的 SSE error。

**“模型生成失败”是我们应用给出的粗粒度提示，不一定意味着网络故障。** 更完整的应用应区分“回答截断”和“调用失败”。

当前代码只将 stop 当作正常完成。笔记整理时上限为 256，实际以 model.py 为准。省略参数也不是无限输出，而是使用提供方默认值。

## 8. 以后看日志，围绕问题找字段

以下路径相对于 event.chunk：

| 想知道什么 | 看哪个字段 |
| --- | --- |
| 刚刚生成了什么？ | choices[0].delta.content |
| 为什么停下？ | choices[0].finish_reason：stop、length、tool_calls 等 |
| 用了多少 token？ | usage：输入、输出、总用量；本次实测最后一块返回 |
| 属于哪次回答？ | id |
| 用哪个模型？ | model |
| 模型请求什么工具？ | choices[0].delta.tool_calls |

从聊天走向 Agent 时，tool_calls 很关键：工具参数也可能分段传来，要收集完整后再执行，把工具结果提交回模型。当前的文本中转程序还没有这个循环。

当前代码将完整 SDK 事件打印在后端终端：

```python
print(f"[LLM event] {event.model_dump_json(indent=2)}", flush=True)
```

indent=2 便于阅读，flush=True 尽快输出。因为包含累计快照，长回答会打印很多重复文字；这并不等于重复的网络传输。

## 回看代码时，记住四句话

1. **LLM 发增量，SDK 在本地累积快照。**
2. **chunk 与 content.delta 是同一个上游片段的不同事件表示。**
3. **stream_reply 等一段、交一段，/chat 包装一段，浏览器追加一段。**
4. **TCP 管字节传输，SDK 管解析与累积，应用管结束状态与用户体验。**

参考：[DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)。本地 SDK 事件定义位于虚拟环境中的 `openai/lib/streaming/chat/_events.py`。
